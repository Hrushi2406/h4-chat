# Deployment

How this app gets to production. **Production is a single self-hosted box**, not Vercel — the app
runs under PM2 behind a Cloudflare tunnel at `tunnel.reelads.pro`.

## Scope: this applies on the production box only

The deploy tooling (`ecosystem.config.js`, `deploy.sh`) is **gitignored and exists only on the
production server**. It is deliberately not in the repo — it hardcodes machine-specific paths.

If you are not on that box, you cannot deploy, and nothing in this file applies. Do not recreate
these files elsewhere or add them to git.

## To ship a change

```bash
cd /home/hrushi-dev/projects/sakhi
git pull
./deploy.sh
```

That is the whole procedure. `deploy.sh` runs, in order:

1. `pnpm install --frozen-lockfile`
2. `pnpm build` — the currently running server keeps serving traffic throughout
3. `pm2 reload ecosystem.config.js --update-env` — rolling worker swap
4. health check on `127.0.0.1:3000`, then `pm2 save` only if it passes

If the health check fails, the script exits non-zero and the **old workers stay up** — PM2 will not
retire them if the new ones fail to bind. Check `pm2 logs sakhi`.

## Rules

- **Never run `pnpm build` by hand on the server.** The build must happen before the reload, not as
  part of it. Building at restart time was the original cause of multi-minute outages on every
  deploy; `deploy.sh` exists specifically to sequence this correctly.
- **Use `pm2 reload`, never `pm2 restart`.** `reload` cycles workers one at a time with zero dropped
  requests. `restart` kills everything first and causes a visible gap.
- **Never edit `~/.pm2/dump.pm2`.** It is generated by `pm2 save`.
- Config changes go in `ecosystem.config.js`, then
  `pm2 reload ecosystem.config.js --update-env && pm2 save`. Editing the file alone does nothing —
  PM2 holds the running config in memory. Omitting `--update-env` silently skips env var changes.

## Layout

| Thing | Location |
|---|---|
| App | `/home/hrushi-dev/projects/sakhi`, port `3000` |
| PM2 config | `ecosystem.config.js` (gitignored) |
| Deploy script | `deploy.sh` (gitignored) |
| Logs | `pm2 logs sakhi`, files in `~/.pm2/logs/sakhi-{out,error}.log` |
| Boot snapshot | `~/.pm2/dump.pm2`, written by `pm2 save` |

The app runs as **2 PM2 cluster workers sharing port 3000**. `pm2 list` showing two `sakhi` rows
(ids 0 and 1) is correct and expected — that is one app, not two. Traffic is round-robined across
both; two workers are also what makes the rolling reload possible.

## Diagnosing

```bash
pm2 list                 # status
pm2 logs sakhi           # live tail (replaces journalctl)
pm2 logs sakhi --lines 200
pm2 describe sakhi       # port, cwd, restart count, log paths
pm2 monit                # live CPU/memory
```

## History

This app previously ran under a systemd unit (`sakhi-app.service`) that had `ExecStartPre=pnpm build`
in the start path, so every restart took the site down for the length of a full Next build. It was
migrated to PM2 cluster mode to get rolling, zero-downtime reloads. The old unit file is backed up
on the box at `sakhi-app.service.bak`.

Known remaining limitation: `next build` rewrites `.next` in place, so during a build an
already-open browser tab can 404 on chunks from the previous build ID. The reload gap is gone; this
window is not. Closing it properly requires blue-green deploys with per-release directories.
